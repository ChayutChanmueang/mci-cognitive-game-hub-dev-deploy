# คู่มือการทดสอบและแนวทางการพัฒนา UX/UI ให้รองรับหน้าจอมือถือหลายอัตราส่วน (Mobile Responsiveness Guidelines)

เอกสารฉบับนี้เป็นผลการศึกษาวิจัยและข้อกำหนดทางเทคนิคเพื่อรองรับการแสดงผลแอปพลิเคชันและมินิเกมบนอุปกรณ์เคลื่อนที่ (Smartphones & Tablets) หลากหลายอัตราส่วนหน้าจอ (Aspect Ratios) โดยแบ่งการจัดการออกเป็นระดับ Global UI (HTML/CSS) และระดับ Game Canvas (Phaser 3)

---

## 1. งานวิจัย: อัตราส่วนหน้าจอมือถือและอุปกรณ์ที่สำคัญ (Mobile Screen Aspect Ratios Research)

จากการวิเคราะห์ส่วนแบ่งการตลาดของอุปกรณ์พกพาในปัจจุบัน อัตราส่วนหน้าจอที่ระบบจำเป็นต้องรองรับแบ่งออกเป็น 4 กลุ่มหลักดังนี้:

### 📊 ตารางสรุปกลุ่มอัตราส่วนหน้าจอที่สำคัญ

| กลุ่มอัตราส่วน (Aspect Ratio Group) | อัตราส่วนทางคณิตศาสตร์ | ตัวอย่างอุปกรณ์หลัก (Target Devices) | ความท้าทายหลักทาง UX/UI |
| :--- | :--- | :--- | :--- |
| **1. Modern Tall Screens** (หน้าจอยาวพิเศษพร้อมติ่ง/รูกล้อง) | **19.5:9** (2.16) ถึง **20:9** (2.22) | iPhone X, 11-15, Samsung Galaxy S20-S24, Xiaomi, Oppo | มีพื้นที่แถบปลอดภัยด้านบน (Notch/Dynamic Island) และแถบควบคุมด้านล่าง (Home Indicator) |
| **2. Legacy/Standard Screens** (หน้าจอมาตรฐานเดิม) | **16:9** (1.77) | iPhone 6, 7, 8, SE (Gen 2-3), มือถือระดับเริ่มต้นทั่วไป | เป็นอัตราส่วนต้นแบบในการพัฒนา หากยืด/หดอาจทำให้ UI ทับซ้อนหรือเกิดขอบดำ (Pillarbox) |
| **3. Tablet Screens** (หน้าจออัตราส่วนกว้าง) | **4:3** (1.33) ถึง **16:10** (1.60) | iPad ทุกรุ่น, iPad Mini, Samsung Galaxy Tab, อุปกรณ์พับได้ (เมื่อกางออก) | หน้าจอมีความกว้างและเตี้ยลงในแนวตั้ง ทำให้พื้นที่ด้านบน/ล่างของเกมน้อยลง เสี่ยงต่อการแสดงผล UI ทับซ้อนกับตัวเกม |
| **4. Foldable & Squarish Screens** (หน้าจอเกือบจัตุรัส) | **1:1** ถึง **5:4** (1.25) | Samsung Galaxy Z Fold (หน้าจอด้านใน), อุปกรณ์พกพาเฉพาะทาง | สัดส่วนมีความเป็นสี่เหลี่ยมจัตุรัสมากที่สุด ต้องการการปรับสเกลองค์ประกอบให้ไม่ล้นหน้าจอ |

## 2. แนวทางการจัดการระดับระบบแสดงผลหลัก (Global UI - HTML/CSS)

ในระดับโครงสร้างเว็บภายนอก (DOM Overlay) ที่ใช้ร่วมกับ Material UI (MUI) และ Custom Vanilla CSS การจัดหน้าจอให้ตอบสนองแบบยืดหยุ่น (Responsive) ดำเนินการผ่านกลไกหลักดังนี้:

### 📱 2.1 การจัดการพื้นที่ปลอดภัย (Safe Area Insets)
หน้าจอสมัยใหม่ที่มี Notch หรือ Dynamic Island จะตัดพื้นที่หน้าจอบางส่วนออก CSS จะต้องใช้ตัวแปร `safe-area-inset-*` เพื่อไม่ให้ปุ่มหรือข้อมูลสำคัญถูกบัง:

```css
/* ป้องกันปุ่มหรือ HUD โดนขอบหน้าจอตัดขาด */
.global-hud-container {
  padding-top: max(16px, env(safe-area-inset-top));
  padding-bottom: max(16px, env(safe-area-inset-bottom));
  padding-left: max(16px, env(safe-area-inset-left));
  padding-right: max(16px, env(safe-area-inset-right));
}
```

### 📏 2.2 การควบคุมหน่วยวัดและการจัดวางแบบยืดหยุ่น (Fluid Layouts)
- **หลีกเลี่ยงการใช้ Fixed Pixels (`px`)**: สำหรับการจัดตำแหน่งระดับสูง ให้เลือกใช้ Flexbox, Grid หรือหน่วยเปรียบเทียบ เช่น `%`, `vh`, `vw`, `vmin` (ค่าที่น้อยกว่าระหว่างความกว้างและสูง)
- **หน่วยขนาดตัวอักษรยืดหยุ่น (Fluid Typography)**: ใช้ฟังก์ชัน `clamp()` เพื่อจำกัดขนาดขั้นต่ำและสูงสุดตามขนาดหน้าจอโดยไม่ให้อักษรซ้อนกัน
  ```css
  h1 {
    font-size: clamp(24px, 4vw + 1rem, 36px); /* ขนาดเหมาะสมกับสายตาผู้สูงอายุ */
    line-height: 1.2;
  }
  ```

### 📺 2.3 การเขียน CSS Media Queries ตามอัตราส่วนหน้าจอ (Aspect-Ratio Queries)
นอกจากการวัดความกว้างเป็นพิกเซลแล้ว ควรระบุการปรับแต่งสำหรับหน้าจอบางกลุ่มด้วยอัตราส่วน:
```css
/* การปรับปรุงเลย์เอาต์เฉพาะสำหรับหน้าจอที่เตี้ยและกว้าง เช่น iPad (Aspect Ratio <= 1.35) */
@media (max-aspect-ratio: 4/3) {
  .sidebar-panel {
    display: none; /* ซ่อนองค์ประกอบไม่จำเป็นเพื่อเพิ่มพื้นที่แนวตั้ง */
  }
  .compact-hud {
    font-size: 16px;
  }
}
```

## 3. แนวทางการจัดการระดับ Game Framework (Phaser 3)

การจัดการโครงสร้างและขนาดตัวเกมที่เรนเดอร์ใน Canvas (Phaser 3) ให้รองรับหน้าจอมือถือหลายขนาด มีกฎการตั้งค่าและการโค้ดดิ้งดังนี้:

### ⚙️ 3.1 การกำหนดสเกลของ Phaser (Scale Manager Configuration)
ในการเริ่มต้นสร้างเกม ควรใช้โหมดการแสดงผลที่ป้องกันภาพบิดเบี้ยวและรองรับสัดส่วนการมองเห็นที่เหมาะสม:

```javascript
const config = {
  type: Phaser.AUTO,
  scale: {
    mode: Phaser.Scale.FIT, // แสดงผลเต็มหน้าจอโดยรักษาอัตราส่วน (Aspect Ratio) เดิมไว้
    autoCenter: Phaser.Scale.CENTER_BOTH, // จัด Canvas ให้อยู่กึ่งกลางหน้าจอเสมอ
    width: 1024, // ความกว้างฐาน (Base Width) สำหรับจัดวางพิกเซล
    height: 768, // ความสูงฐาน (Base Height) สำหรับจัดวางพิกเซล
  }
};
```
*หมายเหตุ:* หากต้องการหน้าจอที่ยืดตามอัตราส่วนอุปกรณ์จริง 100% สามารถเปลี่ยน `mode` เป็น `Phaser.Scale.RESIZE` แต่ทีมพัฒนาต้องคำนวณตำแหน่งพิกเซล (X, Y) แบบไดนามิกทั้งหมด

### 📍 3.2 การหาตำแหน่งวัตถุแบบไดนามิก (Dynamic Anchoring)
**ห้ามเขียนพิกเซลแบบคงที่ (Hardcoded Coordinates)** เช่น `x: 400`, `y: 300` บนองค์ประกอบ UI แต่ให้คำนวณจากขอบจอและจุดกึ่งกลางของกล้องหลัก (Main Camera) เสมอ:

```javascript
// ตัวอย่างการจัดวางปุ่มควบคุมในหน้าจอ Phaser
create() {
  const width = this.scale.width;
  const height = this.scale.height;

  // วางปุ่มโฮมไว้มุมซ้ายบน (ห่างจากขอบจอ 50px)
  const homeBtn = this.add.image(50, 50, 'home-icon');

  // วางปุ่มตกลงไว้กึ่งกลางจอด้านล่าง (ห่างจากขอบจอล่าง 100px)
  const submitBtn = this.add.image(width / 2, height - 100, 'submit-button');
}
```

### 🔄 3.3 การรองรับเหตุการณ์เมื่อหน้าจอเปลี่ยนขนาด (Resize Listener)
เมื่อผู้เล่นทำการหมุนหน้าจอ (Orientation Change) หรือย่อขยายหน้าต่างเบราว์เซอร์ Phaser Scene จะต้องปรับตำแหน่ง UI ใหม่ทันที:

```javascript
init() {
  this.scale.on('resize', this.resize, this);
}

resize(gameSize, baseSize, displaySize, previousWidth, previousHeight) {
  const width = gameSize.width;
  const height = gameSize.height;

  // ทำการคำนวณตำแหน่งของปุ่มและกรอบแสดงผลใหม่ให้สอดคล้องกับขนาดใหม่
  if (this.submitBtn) {
    this.submitBtn.setPosition(width / 2, height - 100);
  }
  if (this.scoreText) {
    this.scoreText.setPosition(width - 150, 50);
  }
}

shutdown() {
  // ยกเลิก Listener ป้องกัน Memory Leak
  this.scale.off('resize', this.resize, this);
}
```

## 4. แผนการทดสอบความลื่นไหลและการแสดงผลมือถือ (Mobile Responsive Test Plan)

เพื่อยืนยันว่าการเปลี่ยนหน้าจอบนอุปกรณ์เคลื่อนที่จะไม่รบกวนการเล่นเกมของผู้สูงอายุ ทีม QA ต้องทำการทดสอบดังนี้:

### 🧪 4.1 ตารางเมทริกซ์การทดสอบจำลอง (Test Matrix)

| # | รายการจำลอง (Device Mockup) | อัตราส่วนเสมือน | วัตถุประสงค์ในการทดสอบ (Test Focus) |
|---|---|---|---|
| 1 | iPhone 13/14/15 Pro | **19.5:9** (แนวตั้ง) | ตรวจสอบว่าแถบด้านบน (Notch) บดบังคะแนนเกมหรือปุ่มกลับหน้าหลักหรือไม่ |
| 2 | iPad Pro 12.9" / iPad (Gen 9) | **4:3** (แนวนอน) | ตรวจสอบว่ามินิเกมแสดงผลไม่ตกขอบบน-ล่าง และปุ่มทางเลือกไม่ทับตัวละคร |
| 3 | Samsung Galaxy Tab A9+ | **16:10** (แนวนอน) | ตรวจสอบสเกล Canvas และการจัดเรียง UI ข้อมูลเชิงสถิติ |
| 4 | Galaxy Z Fold (เปิดกาง) | **~1.2:1** (กึ่งจัตุรัส) | ตรวจทานปัญหาเรื่องระยะห่างของ HUD ด้านข้างไม่บีบแคบจนกดไม่สะดวก |

### 📋 4.2 รายการกรณีทดสอบ (Test Cases)

#### กรณีทดสอบ 1: การหลีกเลี่ยงพื้นที่แถบติ่งจอมือถือ (Notch & Safe Zone Audit)
- **เกณฑ์ยอมรับ (Acceptance Criteria)**: ไม่มีองค์ประกอบ UI หรือปุ่มสำคัญใดๆ ถูกทับหรือตัดขาดจากขอบจอโทรศัพท์ที่มี Notch
- **ขั้นตอนการทดสอบ**:
  1. เปิดโหมด Developer Tools ในเว็บเบราว์เซอร์
  2. จำลองอุปกรณ์เป็น iPhone 14 Pro Max
  3. ตรวจสอบว่า HUD (เวลา, คะแนน) ขยับลงมาด้านล่างอย่างพอเหมาะ ไม่โดนแถบกล้องบัง
  4. ลองหมุนหน้าจอซ้าย-ขวา (Landscape Left/Right) แล้วตรวจสอบว่ากลไกขยับตามทิศทาง Notch หรือไม่

#### กรณีทดสอบ 2: ขนาดปุ่มและการกดสัมผัสสำหรับผู้สูงอายุ (Touch Targets Sufficiency)
- **เกณฑ์ยอมรับ**: ปุ่มกดอินเทอร์แอกทีฟและตัวเลือกคำตอบทั้งหมดต้องมีขนาดไม่น้อยกว่า **48 x 48 px** หรือ **80 x 80 px** (สำหรับเกมหลัก) และห่างกันอย่างน้อย 16px เพื่อป้องกันปัญหานิ้วกดทับกัน (Fatigue/Misclick)
- **ขั้นตอนการทดสอบ**:
  1. เปิดหน้าจอมินิเกมบนจำลองมือถือขนาดเล็ก (เช่น iPhone SE)
  2. ตรวจสอบการวัดขนาดเชิงตัวเลขของปุ่มคำตอบ
  3. ลองใช้คำสั่งสัมผัสเสมือน (Touch Emulation) เพื่อตรวจสอบว่าสามารถคลิกปุ่มได้อย่างแม่นยำ

#### กรณีทดสอบ 3: สัดส่วนการแสดงผลภาพมินิเกม (Game Canvas Scale & Aspect Ratio Fit)
- **เกณฑ์ยอมรับ**: เกมย่อยใน Phaser ต้องขยายเต็มหน้าจอ และคงสัดส่วนที่ถูกต้องเสมอ ไม่เกิดอาการยืดแบน (Stretching) หรือมีองค์ประกอบที่ลอยหลุดจากกรอบพื้นหลังของฉากเกม
- **ขั้นตอนการทดสอบ**:
  1. โหลดหน้าเกมหลัก
  2. ปรับขนาดหน้าจอแสดงผลเบราว์เซอร์ไปมาในหลายอัตราส่วนอย่างอิสระ
  3. สังเกตการตอบสนองของฉากหลังและวัตถุ – ต้องขยาย/หดด้วยอัตราส่วน Aspect Ratio Fit
