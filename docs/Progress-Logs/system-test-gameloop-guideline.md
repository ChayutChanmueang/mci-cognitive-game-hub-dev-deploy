# แนวทางการทดสอบระบบลูปเกม (System Test: Game Loop Guidelines)

เอกสารฉบับนี้เป็นส่วนขยายจาก `system-test-guideline.md` โดยมุ่งเน้นไปที่ **การทดสอบ Core Game Loop** เพื่อให้มั่นใจว่าผู้เล่นสามารถเข้าถึง ยืนยัน และเล่นมินิเกม (Mini-games) ทุกตัวที่กำลังพัฒนาอยู่ได้อย่างราบรื่นตั้งแต่ต้นจนจบ

## 1. วัตถุประสงค์ (Objectives)
- เพื่อยืนยันว่ามินิเกมทุกเกมที่อยู่บน Game Hub สามารถกดเข้าเล่นได้จริงโดยไม่มีข้อผิดพลาด (Broken Links/Crashes)
- เพื่อตรวจสอบวงจรชีวิตของเกม (Game Lifecycle) ตั้งแต่: `หน้าเมนู -> สอนเล่น (Tutorial) -> เริ่มเกม -> จบเกม -> สรุปผล -> กลับหน้าหลัก`
- เพื่อตรวจสอบความถูกต้องของการคำนวณคะแนนและระบบระดับความยาก (Difficulty Scaling)
- เพื่อยืนยันการส่งข้อมูล Event Logs ของเกมกลับไปยังฐานข้อมูล (เช่น Supabase) ได้อย่างถูกต้อง

## 2. ขอบเขตการทดสอบลูปเกม (Game Loop Testing Scope)
การทดสอบลูปเกมของแต่ละเกมจะต้องครอบคลุม State ต่างๆ ดังนี้:
1. **Entry & Loading**: การเชื่อมต่อจาก Game Hub เข้าสู่ Scene ของเกม และการโหลด Assets (รูปภาพ, เสียง)
2. **Pre-game**: หน้าต่าง Tutorial, การเลือกความยาก (EASY, NORMAL, HARD)
3. **Gameplay**: กลไกหลักของเกม (Core Mechanics), การควบคุม (Input), ระบบฟิสิกส์หรือเงื่อนไข (Win/Loss Conditions)
4. **Pause/Resume**: การหยุดเกมชั่วคราวและการกลับมาเล่นต่อ (ถ้ามี)
5. **Post-game**: หน้าต่างสรุปผลคะแนน (Result/Score Board), ปุ่มเล่นใหม่ (Retry) และปุ่มกลับหน้าหลัก (Back to Hub)

## 3. ขั้นตอนการทดสอบลูปเกม (Step-by-Step Game Loop Testing)

สำหรับ **ทุกๆ มินิเกม** ที่กำลังพัฒนา ทีมทดสอบจะต้องดำเนินการตาม Flow ดังต่อไปนี้:

1. **เข้าสู่ Game Hub**: เข้าสู่ระบบและตรวจสอบให้แน่ใจว่ารายชื่อเกมปรากฏขึ้นครบถ้วน
2. **กดเข้าเกม (Game Entry)**: 
   - คลิกที่เกมที่ต้องการทดสอบ
   - *Expected*: ต้องโหลดเข้าสู่หน้า Title หรือ Tutorial ของเกมนั้นๆ โดยหน้าจอไม่ดำและไม่มี Error ใน Console
3. **ทดสอบระดับความยาก (Difficulty Test)**:
   - กรณีที่เกมมีให้เลือกระดับความยาก ให้ทดสอบเข้าเล่นทีละระดับ (EASY, NORMAL, HARD)
   - *Expected*: ความเร็ว, จำนวนศัตรู หรือเงื่อนไขต้องเปลี่ยนไปตามระดับความยากที่เลือก
4. **ทดสอบระบบการเล่น (Gameplay Test)**:
   - ทดสอบการกระทำที่ทำให้ "ได้คะแนน" (Positive Feedback)
   - ทดสอบการกระทำที่ทำให้ "เสียคะแนน/เสียชีวิต" (Negative Feedback)
   - *Expected*: แอนิเมชัน เสียงประกอบ และตัวเลขคะแนน/ชีวิต (UI) ต้องอัปเดตแบบ Real-time
5. **ทดสอบเงื่อนไขการจบเกม (End Game Test)**:
   - ปล่อยให้เวลาหมด หรือ ใช้ชีวิต (Lives) จนหมด
   - *Expected*: เกมต้องตัดเข้าสู่หน้าสรุปผล (Game Over / Result Scene) อย่างถูกต้อง และแสดงคะแนนสุทธิ
6. **ทดสอบการเชื่อมต่อ API (Logging Validation)**:
   - เปิด Developer Tools (Network Tab) ในระหว่างที่เกมจบ
   - *Expected*: ต้องมีการส่ง Request บันทึกคะแนนและ Log ไปยัง Supabase (Status 200/201)
7. **ทดสอบการกลับหน้าหลัก (Exit Flow)**:
   - กดปุ่ม 'ออกจากเกม' หรือ 'กลับสู่เมนูหลัก'
   - *Expected*: ระบบพากลับมาที่ Game Hub พร้อมสถานะที่อัปเดต (เช่น เปลี่ยนสถานะด่านเป็น "ผ่านแล้ว")

## 4. Checklist สำหรับการทดสอบ Game Loop ทุกเกม
ก่อนพิจารณาว่ามินิเกมนั้น "พร้อมใช้งาน (Ready)" ต้องผ่าน Checklist ต่อไปนี้:

- [ ] โหลด Assets ครบถ้วน (ไม่มีรูป/เสียงหาย หรือ Error 404 ใน Network)
- [ ] ปุ่ม UI ทั้งหมดในเกมสามารถกดได้จริงและตอบสนองถูกต้อง
- [ ] (ถ้ามี) หากผู้เล่นกดสลับ Tab Browser เกมสามารถ Pause ตัวเองได้ (Visibility API)
- [ ] คะแนนคำนวณถูกต้องตามกติกาของเกม
- [ ] เกมโอเวอร์และแสดงหน้าสรุปผลได้โดยที่ Browser ไม่ค้าง (ไม่มีอาการ Memory Leak)
- [ ] ข้อมูลคะแนน/สถิติ ถูกส่งไปยัง Database (Supabase) อย่างสมบูรณ์ ไม่มี Error 400/500
- [ ] สามารถกดกลับมาที่หน้า Game Hub และเลือกเล่นเกมอื่นต่อได้ทันทีโดยไม่ต้อง Refresh หน้าเว็บ (Scene เปลี่ยนสลับได้สมบูรณ์)

## 5. การจัดการ Automated Testing สำหรับลูปเกม (ถ้ามี)
เนื่องจากการทดสอบ Gameplay ภายใน Canvas ทำได้ยากด้วย E2E Tools ปกติ แนวทางที่ดีที่สุดคือ:
- **Unit Test**: ทดสอบ Logic ฝั่งคณิตศาสตร์ของการบวก/ลบคะแนน
- **E2E (Playwright/Cypress)**: ทดสอบว่ามี DOM Element ของ Canvas ปรากฏขึ้น, มีปุ่ม UI แบบ HTML Overlay ครบถ้วน, และทำการดักจับ (Intercept) Network Request เพื่อยืนยันว่ามีการส่ง Log Event ไปยัง Database จริงเมื่อจบเกม
