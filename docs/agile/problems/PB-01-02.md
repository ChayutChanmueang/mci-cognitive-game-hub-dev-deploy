# Problem Record: PB-01-02 — Boot loading overlay stayed up too long (waited for full data load, not first paint)

**Problem ID:** PB-01-02 (Problem #01 *Routing & async data-load races* → sub-problem #02)
**Status:** ✅ Fixed (2026-06-26)
**Severity:** 🟠 Medium (UX — slow perceived startup)
**Related:** [PB-01-01](./PB-01-01.md) (introduced the boot overlay), [BUG-005](../reports/bugs/BUG-005.md)
**Affected files:** `src/main.js` (boot + `showHub`), `src/ui/game-hub-screen.js` (`renderGameHubScreen`)

---

## 1. Symptom
หน้า loading ตอนเปิดแอปค้างนานมาก ~10–20 วินาที กว่าจะหาย ทั้งที่หน้าจอน่าจะพร้อมเร็วกว่านั้นมาก

## 2. Root cause (ทำไมถึงนาน)
The boot overlay was dismissed when the boot's `firstRender` promise resolved — and for the Game Hub that promise is the **whole** `renderGameHubScreen()` promise:

```js
render();              // ← hub is ALREADY painted & usable here (synchronous)
await loadProgram();   // ← but the overlay kept waiting through these…
await loadHistory();   //    …slow DB loads (seconds each)
```

So the overlay stayed up until **every** Game Hub database load finished, not until the hub was visible. On a slow connection that's many seconds, and the **8s/12s safety timeout** often became the thing that finally hid it — making boot feel 10–20s.

> **Anti-pattern:** *gating a "screen is ready" signal on the screen's full data load instead of its first meaningful paint.* A progressively-rendered screen is usable after its first `render()`; the remaining data fills in afterward and must not block the loading indicator.

## 3. Fix
Dismiss at **first paint**, let data load in the background:
- `renderGameHubScreen()` now calls an `options.onReady?.()` callback **right after the initial `render()`** (before `loadProgram`/`loadHistory`).
- `showHub` passes `onReady: finishBootLoading` (idempotent + once-guarded, so it's safe on every hub navigation).
- Safety-net timeout tightened `12s → 8s` (it's now only a last resort; normal dismissal is ~1–2s).

The boot's `firstRender.finally(finishBootLoading)` still exists as a fallback, but `onReady` fires first for the hub, so the overlay no longer waits for the data loads.

## 4. How to avoid this in the future (กฎ)
- A loading/splash indicator must be dismissed on **"first usable paint"**, not on "all data loaded". Expose an explicit **`onReady`/`onFirstPaint`** signal from progressively-rendered screens and dismiss on that.
- Keep a **safety timeout** as a backstop, but treat it as a *bug indicator* — if it's the thing hiding your loader, your ready-signal is wired to the wrong moment (as it was here).
- When a screen renders a skeleton then hydrates, never `await` the hydration before signalling readiness.

## 5. Verification
- `node --check` both files + `npm run build-nolog` pass.
- Manual: on a throttled connection the overlay now clears as soon as the hub appears (~1–2s), and the game list/history populate a moment later without blocking.
