# Problem Record: PB-01-01 — Stale async route handler renders over the current screen ("bounce back to Game Hub")

**Problem ID:** PB-01-01 (Problem #01 *Routing & async data-load races* → sub-problem #01)
**Status:** ✅ Fixed (2026-06-26)
**Severity:** 🔴 High (functional / UX blocking)
**Related Bug:** [BUG-005](../reports/bugs/BUG-005.md)
**Affected files:** `src/main.js` (route dispatcher + `showHub`), `src/ui/game-hub-screen.js` (`renderGameHubScreen`)

---

## 1. Symptom (what the user saw)
เมื่อข้อมูลโหลดช้า แล้วผู้ใช้กดทำอย่างอื่น **ก่อน** ที่ Game Hub จะโหลดเสร็จ ระบบจะ **ดีดกลับมาหน้า Game Hub**:
- **กรณี A:** กดเปิดมินิเกมก่อนข้อมูลโหลดเสร็จ → พอโหลดเสร็จเด้งกลับ Game Hub
- **กรณี B:** อยู่หน้า Game Hub (ที่ยังโหลดไม่เสร็จ) แล้วเปิดหน้า Leaderboard → เด้งกลับ Game Hub

---

## 2. Root cause (ทำไมถึงเด้งกลับ)
The route dispatcher `renderCurrentRoute()` in `src/main.js` bumps a counter `routeRenderVersion` on **every** route change, and async route handlers `await` their data before rendering. **But only the `game` route re-checked `routeRenderVersion` after its awaits** — the screen handlers (`showHub`, and `renderGameHubScreen`'s post-load re-renders) did **not**.

So the sequence that bounces the user:

```
boot → renderCurrentRoute(hub)         routeRenderVersion = 1
       └ showHub() starts, awaits db.getPatientByHn(...) + renderGameHubScreen(...)  ← SLOW
user taps a game / leaderboard
     → renderCurrentRoute(game|leaderboard)   routeRenderVersion = 2
       └ new screen renders correctly
       ...meanwhile the OLD showHub() (version 1) finishes awaiting...
       └ it calls render()/renderGameHubScreen() UNCONDITIONALLY
         → paints the Game Hub on top of the screen the user actually moved to  ← BOUNCE
```

Extra wrinkle: `renderGameHubScreen()` itself renders **once synchronously**, then **re-renders again** after its own `await loadProgram()` / `await loadHistory()`. Even if the caller checks staleness once, those later internal re-renders could still paint over a newer route. So the stale-render window exists in **two** layers (the handler, and the component's post-load re-renders).

> **The anti-pattern in one line:** *an `async` function that `await`s data and then writes to the shared DOM (`uiRoot.innerHTML`) without re-checking whether its route/render is still the current one.* The last writer wins — and a slow handler is often the last writer.

---

## 3. Fix applied
A **route-version guard** (the project already had the pattern in the `game` route — we extended it):

1. **`showHub` (`src/main.js`)** — snapshot `const renderVersion = routeRenderVersion;` at entry; after the `await db.getPatientByHn(...)` load, `if (renderVersion !== routeRenderVersion) return;` so a stale handler stops before doing any rendering.
2. **`renderGameHubScreen` (`src/ui/game-hub-screen.js`)** — accepts an `isStale` callback; the shared `render()` returns early when `options.isStale()` is true. `showHub` passes `isStale: () => renderVersion !== routeRenderVersion`. This neutralises **all** render() calls (initial + every post-load re-render) once the route has moved on.

Net effect: the Hub can no longer paint itself over a newer screen → no more bounce. This alone resolves the root cause (BUG-005's option B: "don't redirect/re-render back to the Hub").

**Complementary measure (added per a separate product requirement, 0.13.0):** a **boot loading overlay** (modal, markup in `index.html`) now blocks interaction until the first screen has fully rendered, so the user cannot tap a game/leaderboard *during* the initial load at all. To dismiss it only when ready, `navigateTo()` returns the `renderCurrentRoute()` promise and the in-dispatcher redirects `return navigateTo(...)` so the boot promise chains through redirects to the final screen; `finishBootLoading()` then hides it (with a 12s safety timeout). This is defence-in-depth — the route-version guard is still the actual fix; the overlay improves the boot UX and covers other interaction-during-load races.

---

## 4. How to avoid this in the future (กฎที่ต้องทำตาม)
**ทุกครั้งที่ handler เป็น `async` แล้วจะ `await` ข้อมูลก่อน render ลง `uiRoot`/DOM ร่วม ต้องทำ staleness check:**

- Snapshot `routeRenderVersion` (or pass a `renderVersion`/`isStale`) at the **start** of the handler.
- After **every** `await`, and immediately **before any DOM write**, re-check it and **bail if stale**.
- If the render lives inside a component that re-renders after its own awaits (เช่น `renderGameHubScreen`), pass an `isStale` callback **into** the component and guard its `render()` — guarding only at the call site is not enough.
- Prefer **not** re-navigating (`navigateTo(ROUTES.hub)`) to "recover" — just abort the stale render and let the current route stand.

**Handlers to audit for the same pattern (apply the same guard if they `await` before rendering):** `showTestGameHub` (mirror of `showHub`), `showPlayerInfo`, `showCheckInSummary`, `showSignup`. `showLeaderboard` renders synchronously (no pre-render `await`) so it cannot be stale by itself — it was only ever the *victim* of a stale `showHub`.

- `node --check` on both files + `npm run build-nolog` pass.
- Manual repro (throttled network): open a game / leaderboard before the Hub finishes loading → no bounce back to the Hub.
