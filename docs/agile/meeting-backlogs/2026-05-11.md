## 2. Agenda & Discussion Points

### 2.1 Database Field Standardization (ฝั่ง Web & DB)
**Reference:** [Data Schema](../../software/03-data-schema.md)
เพื่อให้การบันทึกข้อมูลเป็น Format เดียวกันตลอดทั้งระบบ:
- **Case Style**: ตกลงใช้ **snake_case** สำหรับ Column ใน Database (เช่น `started_at`, `user_game_data_id`)
- **Boolean Naming**: แก้ไขความสับสนของฟิลด์เช็คชื่อ ให้ใช้ `check_in` (snake_case) แทนการใช้ `check-in` (kebab-case) เพื่อลดปัญหาในการเขียน Query
- **Birth Date**: กำหนดให้ใช้ชื่อฟิลด์ `birth_date` (ปัจจุบันใน Code ใช้ `date`) เพื่อความสื่อความหมายที่ชัดเจน
- **Mandatory Fields**: สรุปฟิลด์ที่ต้องมีในการสร้าง Patient Profile (`hn`, `firstname`, `lastname`, `phone`, `birth_date`, `gender`, `education_level`)

### 2.2 Game Data Collection (ฝั่ง Game -> Web)
**Reference:** [Data Reference Guide](../../software/03-data-reference.md)
ประเด็นว่า Minigame จะเก็บข้อมูลอะไรบ้าง และ Web จะนำไปใช้อย่างไร:
- **Core Metrics**: ทุกเกมต้องส่ง `score`, `level`, `started_at`, `ended_at` กลับมาเสมอ
- **Success Payload**: เมื่อเล่นจบ เกมจะเรียก `pushGameData` เพื่อส่ง JSON นี้ไปบันทึก
- **Data Utilization**: ฝั่ง Web จะนำ `ended_at - started_at` มาคำนวณ "เวลาที่ใช้เล่น" เพื่อแสดงในกราฟพัฒนาการ
- **Difficulty Tracking**: ฝั่ง Web จะต้องดึงค่า `level` มาแสดงเพื่อระบุว่าผู้ป่วยมีศักยภาพอยู่ในระดับใด (Easy/Normal/Hard)

### 2.3 Shared Data & Interaction (ประเด็นที่ต้องแชร์กัน)
- **Session Bridge**: ทั้ง 2 ทีมต้องใช้ `sessionStorage` ร่วมกันผ่าน Key มาตรฐาน:
    - `selected_game_gid`: เพื่อให้ Phaser รู้ว่าต้องโหลดเกมไหน
    - `patient_login_id`: เพื่อให้ Phaser รู้ว่าต้องบันทึกคะแนนให้ใคร
- **Error Handling**: หาก Minigame บันทึกคะแนนไม่สำเร็จ (เช่น Internet หลุด) ควรมีระบบ Retry หรือเก็บข้อมูลไว้ใน LocalStorage ก่อนหรือไม่?
- **MCI Group Mapping**: การแสดงผลสีและ Icon ในหน้า Web Hub ต้องตรงกับ `mci_group` ที่ระบุใน `game_list_data`
